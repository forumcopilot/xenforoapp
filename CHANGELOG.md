# Changelog

All notable changes to this project are documented in this file.

The format is inspired by [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Releases below 1.0 should not be assumed backward-compatible across minor bumps; from 1.0 on, what each kind of release may change for a fork is in [RELEASING.md](RELEASING.md#versioning).

## [Unreleased]

### Bundled addon, not yet released (after v1.11.0)
- `getConfig` names the forum, so the app can add a forum from its address alone: `boardTitle` and `boardUrl` (XenForo's options), `boardIcon` (the default style's app icon, large first, else its favicon, as an absolute URL; empty when the style has none) and `siteId` (the site id forumcopilot.com gave the forum; empty until the add-on's options are saved). Checked on XenForo 2.2.19 and 2.3.7, with and without an icon set.
- `getThread` (and `getThreadByPost`, `getThreadByUnread`) sends the thread's `tags`, the names its page lists, and `emailSubscribe`, whether the member's watch also sends emails, so the app's Watch sheet no longer calls `subscribeTopic` just to read it. Thread and topic-row `tags` are empty while the forum's tagging is off, as on the website (topic rows sent them anyway in 1.11.0). `FCThreadResult` declares both keys.
- Posts in the thread methods carry XenForo's "Last edited" line: `lastEditDate` (ms; 0 when the post shows none, which follows XenForo's "Display 'last edited' message" option) and `lastEditByModerator` (the website then says "Last edited by a moderator"; it never names the editor, so neither does the API). Posts and direct messages carry `authorTitle`, the title under the author's name as the website shows it: the custom title, else the group title or title ladder, the guest group's title for guests, and empty where the forum hides titles of members who have a banner. XenForo keeps no edit date for direct messages.
- `contentHtml`: `data-media-url` is the media's page for every media site XenForo ships, built from the key as XenForo writes it (YouTube start time and playlist, Vimeo private links and start time, Dailymotion start time, Twitch clips, videos and channels, Spotify types, Facebook posts, videos and fb.watch links, Reddit, SoundCloud, Tumblr, Flickr and Bluesky through their oEmbed URL schemes). 1.11.0 sent none for Vimeo, Facebook, Flickr, Reddit and Bluesky, and a wrong one for GIPHY, TikTok and keys with a start time, a path or a type. Posts on X are `https://x.com/i/status/{id}` (was `twitter.com/statuses/{id}`), TikTok videos `https://www.tiktok.com/@/video/{id}`. Other media sites get an address from their own oEmbed URL scheme or match URLs (plain or regex), only one that the site's patterns read back as the same key; otherwise it is empty.
- Checked on XenForo 2.2.19 and 2.3.7 against the website's own thread and direct-message pages: the titles (the title ladder, group titles, a custom title with `&` and `<`, titles hidden behind banners), "Last edited" by the author and by a moderator, tags with tagging on and off, and watching with and without email. Media addresses were checked for each built-in site's key formats and for custom sites with plain, wildcard, regex and oEmbed patterns. The test data was removed by restoring the databases.

### Bundled addon (v1.10.0 → v1.11.0, the `addon-v1.11.0` release)
- A review of all 105 API methods against XenForo's own pages and services; each method now does what the matching XenForo page does. New behaviour comes as new response fields and new optional params, plus three new methods for ignoring members, so a 1.x app keeps working; where a 1.x app sees a difference, it is a fix (listed below). `docs/API-Index.md` describes every method as it now is.
- Errors: every refusal answers HTTP 200 (the app reads `resultText` only from 2xx replies), including "log in first" (was 401), flood checks (was 429) and the dispatcher's own errors. Requests must be JSON with the media type `application/json`. Replies carry `Content-Type: application/json` (it was `unknown/unknown`).
- Account: `updateProfile` changes only the member's own profile, and keeps a date of birth that is already complete. Passkey sign-in checks origin, signature counter and attempts as XenForo does, and trusts the device so the remember cookie signs the app back in; password sign-in asks for two-step only when XenForo would. The app's two-step trust lasts a new option's number of days ("App two-step trust (days)", 365) instead of until 2100, and signing out or deleting the account ends it. Password, email and account-deletion checks count wrong passwords like XenForo's login. `forgotPassword` follows the lost-password page (on forums that show guests a captcha it points to the website, `resetViaWebUrl`). `register` checks required custom fields, reports a sign-up the spam check rejected, and refuses a signed-in member. The account methods, like XenForo's account pages, work for a member waiting for email confirmation. Settings use XenForo's labels and defaults. `doLoginMod` no longer signs anyone in (no app calls it; moderators sign in with `login`).
- Devices: a reused FCM token moves to the device that registers it last; a signed-out app can unregister with `deviceId` and `fcmToken`; a password change, ban, rejection or deletion removes the member's device registrations (two new entity extensions), and a daily cron removes stale ones.
- Members: `getUserInfo`, `searchUser` and `getOnlineUsers` follow XenForo's privacy settings (online status, current activity, full profile, custom fields, groups and account state). `getUserInfo` sends real follower and following counts, `canFollow`, `canPostOnProfile` and `customFieldsDisplay`. `getUserReplyPost` pages without repeats, counts only posts the member may see, follows profile privacy and returns at most 50. `searchUser` takes `match: "prefix"`.
- Moderation: approve uses XenForo's approver (forum watchers are notified; a deleted thread must be undeleted instead); undelete checks the content is viewable; delete and move read their options as XenForo's forms do (new `authorAlert`, `redirectLength`, `starterAlert`, `notifyWatchers`, `prefixId`); `banUser` reads `endDate` in the moderator's time zone and takes an exact `endTime`.
- Threads and posts: members can report posts (`canReport` was always false). Thread pages are ordered as XenForo orders them, capped at 100 posts, count the view, clear the alerts about the posts shown, mark ignored members' posts (`isIgnored`), apply the forum's censored words, and cost about ten queries instead of about two per post. New optional `includeHidden` lists moderated and deleted posts to those who may see them. New fields: `signature` (by the member's "show signatures" choice), `isAuthorOnline`, thread type, solution and votes for question and suggestion threads, attachment types. `replyPost` and `saveRawPost` run XenForo's spam and flood checks, delete the reply draft, and save again when a post already has attachments; `saveRawPost` takes `silent` and `authorAlert`. Quotes, reports and poll votes work as on the website.
- Topics and forums: `newTopic` runs XenForo's flood and spam checks and takes tags, custom thread fields, a poll and a thread type; `getForum` says what each forum requires and allows, and whether and how the member watches it. `getTopic` takes XenForo's sort orders and filters. Topic rows report locked and deleted threads, lists leave out forums the member can't read and are capped at 100 rows, and a list costs a few queries instead of several per row. A guest who may not read a forum's threads gets `guest_denied`. "Mark read" works on categories.
- Subscriptions: `getSubscribedForum` works in the app (`subscribeMode` was text where the app reads a number). `getSubscribedTopic` lists exactly the watched threads. Subscribing again no longer overwrites watch options set on the website; new optional `notifyOn`, `sendAlert`, `sendEmail` and `emailSubscribe`.
- Direct messages: replies need the member to be in the conversation; attachments follow the direct-message upload permission; recipients who don't exist or don't accept messages are named in the error; flood checks; the reply draft is deleted; editing a message with attachments works again; `unreadCount` is the number of unread conversations; rows list their participants; message pages load attachments and reactions per page.
- Search: all four methods run on XenForo's search (index, minimum word length, result limit, cache, permissions before counting); topic results are full topic rows; `searchId` pages through the same results; `searchTopic` returned its results in the wrong field.
- Alerts and reactions: `getAlert` pages through every alert (`total` was the page's count) and takes `skipMarkRead`, `unreadOnly`, `markReadIds`, `markUnreadIds` and `markAllRead`, with XenForo's read state in `isUnread`. Reactions must exist and be active, and refusals give XenForo's reason. `follow` checks what XenForo's follow button checks.
- `getConfig`: guest search and the online list are reported correctly (always false before); new fields for search settings, the visitor's capabilities, notices (dismissible with `dismissNoticeId`), help and policy pages, and whether updated terms must be accepted.
- Ignore a member (App Store guideline 1.2): three new methods, `ignoreUser`, `unignoreUser` and `getIgnoredUsers`, as XenForo's Ignore button and account page; `getConfig`'s `ignoreUser` is now true. Posts and messages already say `isIgnored`.
- Posts and direct messages as HTML: with the new optional `contentHtml: true`, the thread and conversation methods also send each post or message (and signature) rendered by XenForo (`contentHtml`, `signatureHtml`): the forum's custom BBCodes, media sites, smilies and censored words as on the website, as plain HTML with absolute URLs and data attributes on quotes, mentions, attachments, media, spoilers and link previews (`BbCode/Renderer/AppHtml.php`, based on XenForo's REST API renderer). The BBCode in `content` is still sent.
- Uploads use XenForo's temporary files; an avatar's extension must be an image type.
- Removed: `App.php`, an unused second copy of the method list (an upgrade step deletes it), and unused result and param classes.
- Verified by building the release ZIP with XenForo's packer (186 files, identical to `upload/`) and upgrading the published 1.10.0 → 1.11.0 with `xf-addon:upgrade` on XenForo 2.2.19 and 2.3.13: XenForo's file health check passes, the web-root `forumcopilot.php` matches the archive, `App.php` is removed, and the new option, cron entry and two class extensions are in place. An API test suite of about 830 checks, one or more per change, with the data each needs (spam phrases, custom fields, question and suggestion forums, censored words, signatures, moderated and deleted content, notices, tags, permissions, flood limits), passes on both: 832/832 on 2.3.13 and 827/827 on 2.2.19 (the few skipped checks need outside spam services or the Forum Copilot backend). Live suites on 2.3.13: basic 49/49, interface 87/100 (the 13 are its moderator tests running as an ordinary member, and member tests after its own email change). The test data was removed by restoring the databases.
- Every `result: false` reply has an `errorCode` next to `resultText`, so the app can tell kinds of error apart without reading the text: `login_required`, `guest_denied`, `no_permission`, `not_found`, `validation`, `flood`, `board_closed`, `banned`, `account_pending`, `account_disabled`, `tfa_required`, `security_locked`, `bad_request`, `server_error`, or `error` for anything else (`Api/ErrorCode.php`). Form errors that XenForo keys by field also come as `errors` (field => message), as `register` already did. Unexpected errors are written to XenForo's server error log under a short reference, and the reply says "An unexpected error occurred" with that reference (`errorId`) instead of the error's own text. XenForo's own refusals (not found, no permission, a service's validation errors) keep XenForo's message, which also fixes four not-found errors that showed a phrase name ("thread_not_found") instead of text. Errors the dispatcher catches answer HTTP 200 like the controllers' errors, so the app shows their text.
- Threads started or replied to in the app are watched by the member's own "watch content on creation" and "on interaction" preferences, as on the website (`autoWatchThread` after `newTopic` and `replyPost`). Before, the app never watched them, so a member who started a thread in the app got no alerts or pushes for its replies. Exercised as a regular member on 2.2.19 and 2.3.7 with the preferences set (watched, with and without email as chosen) and unset (not watched).

### App: the add-on 1.11.0 features (ported from the official app's Phase 2)

Quotes, code blocks (coloured by language, with a copy button), headings, spoilers, tables and media embeds follow Flapp and the Discourse app: video sites as their picture with the site's play button. The forum's inline styles keep their fill, and XenForo's font menu maps to fonts the device has.

### Fixed
- Closing the Reply page with ✕ (or Back) with something written asks what to do with it: Discard, Save draft or Cancel. It used to keep it without asking and put it back in the thread's quick-reply bar, where the only way to remove it was to select it all and delete it. Discard now empties the bar and removes the draft, on this device and on the forum; Save draft puts it back in the bar. The same for a direct-message reply. Tests: `test/reply_editor_close_test.dart`, `test/discard_changes_scope_test.dart`.
- The thread comes back with the keyboard down when the Reply page closes, whether the reply was posted, discarded or saved. The quick-reply bar took focus back if it had it when the Reply page opened (typing in it, then Reply on a post), and the keyboard came straight back up over the thread.
- A quote reply keeps the same editor when the quote arrives. It was built anew, which put the keyboard away and brought it back.
- Dragging a thread or a conversation while the keyboard is up also tells the system to hide it. On an iPhone the keyboard could stay up over a thread however it was scrolled (reported after closing the Reply page). Test: `test/quick_reply_bar_test.dart`.

## [1.0.1] - 2026-10-26

A patch release: the newer bundled add-on, and one fix in the app. Members who sign up on the forum's website from the app now come back signed in, and in-app sign-up follows the forum's spam protection. The app's sign-in request is kept in XenForo's session (from `forumcopilot-app-login`, or the app's `_xfRedirect` on the register page or a connected-account sign-up), and `register/complete` shows "Continue in the app", which hands the app a code as the sign-in page does. ## [1.0.0] - 2026-10-19

The 1.0 release, the same app as the official Forum Copilot app 1.0. Since 0.10.2 it has taken the official app's 0.10.3 to 1.0: the reactions and Material 3 work from the Discourse-app review, the forum's own header and colours, reply bars in threads and conversations, sign-in on the forum's website, two-step and passkeys from another phone, account deletion, drafts shared with the web editor, notification channels, and the fixes from reviewing every screen on a Pixel 4a and an iPhone 17. Ships with bundled ForumCopilot addon **v1.9.0**; the features that need it stay off with an older add-on. From this release on, versions follow the rules in [RELEASING.md](RELEASING.md#versioning).

A public `forumcopilot-app-login` page hands the app a one-time code through a URL scheme listed in the new option `fc_app_login_schemes` (default `forumcopilot`, the official app's scheme); `getConfig` reports the list as `browserLoginSchemes`.

- `getConfig` sends the forum's colours and logo as `style`.
- Fixed: `getConversations` returned the wrong page from the second load onwards; direct messages posted in the same second now get their own numbers; changing the password from the app keeps the app signed in.
- The phrases and templates added for these were stamped 1.8.12 on their branch; 1.8.12 shipped without them, so they are stamped 1.9.0, the version that brings them.

### Bundled addon (v1.8.11 → v1.8.12, published 2026-10-16 as the `addon-v1.8.12` release)
- `replyPost` and `newTopic` report a post or thread held for moderator approval as `state: 1`. They returned `$thread->canView() ? 0 : 1`, and XenForo lets the author view their own moderated content, so a reply or thread waiting for approval always came back as `state: 0` and the app treated it as published. They now read the post's `message_state` and the thread's `discussion_state`. Verified on 2.2.19 through `forumcopilot.php` as a regular member in a forum set to moderate new threads and replies: with 1.8.11 the reply and the thread were stored as `moderated` and both answers said `state: 0`; with this change both say `state: 1`, and a reply in an unmoderated forum still says `state: 0`. On 2.3.7 the change was deployed and `getConfig` answered; no member account there to post with. No new error-log rows on either. The test posts were removed by restoring the database.
- Verified by building the release archive (a zip of `upload/`, the same 191 files as 1.8.11) and upgrading 1.8.11 → 1.8.12 on 2.2.19 and 2.3.7 with `xf-addon:upgrade`: XenForo's file health check passes for every add-on file on both, and the web-root `forumcopilot.php` matches the archive. Live basic suite on 2.2.19: 49/49. The only new error-log rows are the test forum's push attempts, blocked on purpose during the run.

### Bundled addon (v1.8.9 → v1.8.11, published 2026-10-15 as the `addon-v1.8.11` release; includes 1.8.10, which was not released separately)
- XenForo 2.2: the "who reacted" list on direct messages was always empty, so the app could not show which reaction anyone had given on a message. `getConversationMessageLikesInfo` returned nothing unless `\XF\Repository\ReactionRepository` existed, which is XenForo 2.3's name (2.2 calls it `\XF\Repository\Reaction`); 1.8.4 fixed the same check for posts but missed this copy. It also read `emoji_shortname`, a column 2.2 does not have, which would have dropped every entry with a logged error. It now accepts either class name and uses the emoji and icon helpers that posts and `getConfig` already use, so posts, messages and the reaction picker agree. On 2.3 nothing changes. Verified on 2.2.19 and 2.3.7 by upgrading 1.8.9 → 1.8.11 and reacting to a direct message through `forumcopilot.php`: on 2.2.19 with 1.8.9 a Wow was stored (`reaction_id` 4) but `likesInfo` was empty; with 1.8.11 it lists the member with Wow 😮, then Love ❤️ after switching, and removing it works. On 2.3.7 the response is the same before and after (Wow 😲). No new error-log rows on either.
- `likeCount` is now the number of reactions on a post or direct message, not XenForo's `reaction_score`. The score sums each reaction's score, and XenForo's stock Wow, Sad and Angry score 0, so a post or message whose only reaction was a Wow reported 0 and the app hid its reaction row (it showed for a moment after reacting, then the server's count removed it), Like + Wow reported 1, and a custom negative reaction could make it negative. Every place that reports it reads the `reactions` counts through one helper (`AbstractController::getReactionCount`): posts and threads in `getThread` and friends, search results, conversation messages, and the react / unreact responses for posts and messages. Forums that only use Like see no difference. Verified on 2.2.19 and 2.3.7 through `forumcopilot.php`, on a thread's first post and on a direct message: before, a Wow gave 0 and Wow + Like gave 1; after, 1 and 2, removing them gives 1 then 0 (`likePost` toggle and `unlikePost`, `unlikeConversationMessage`), and the thread's own `likeCount` follows its first post. No new error-log rows. App builds already show the server's count, so 0.10.2 picks this up without an update.
- Test forums can point the add-on at another Forum Copilot API. If `src/config.php` sets `$config['forumCopilot']['apiUrl']`, the add-on registers, validates its connection and opens SSO against that base URL instead of `https://forumcopilot.com/api` (`BackendApi::apiUrl()`, used by all six outbound calls). Live forums never set it and behave exactly as before. Used by the staging test forum.
- Verified by building the release archive (a zip of `upload/`, like 1.8.9) and installing it with XenForo's own archive installer (the job behind **Install/upgrade from archive**): on 2.2.19 as an upgrade from 1.8.9, on 2.3.7 as a same-version rebuild. Every add-on file, the smart-banner assets and the web-root `forumcopilot.php` match the archive, and XenForo's file health check passes for the add-on on both. Live API suites, run as Admin: 49/49 and 100/100 on 2.2.19 and on 2.3.7. The only new error-log rows are the test forums' own push misconfiguration (not registered with the push service), unrelated to this release.

### Bundled addon (v1.8.7 → v1.8.9, published 2026-10-13 as the `addon-v1.8.9` release; includes 1.8.8, which was not released separately)
- One push per direct message. On XenForo 2.3, a conversation started or answered from the app reached the recipient's phone three times: once from the add-on's message listener (sender as title, message preview as body), which is the one to keep, and twice as "X sent a direct message … to you" from the add-on's extension of XenForo 2.3's conversation `PusherService`. That extension pushed on every run of XenForo's conversation notifier, and the notifier ran twice because `newConversation`, `replyConversation` and `inviteParticipant` called `sendNotifications()` after `save()`, although XenForo's conversation services already send them inside `save()`. That double call also e-mailed every recipient twice, on 2.2 as well. The extension's push also skipped the router, so it went to the hosted backend even with hosted push turned off, and never reached direct-mode (own Firebase) devices. Now the listener is the only source of new-conversation and reply pushes on 2.2 and 2.3. It also runs after XenForo REST API requests (`app_api_complete`), which 2.3 used to cover only through the extension. It follows XenForo's own push rules: no push to a member who turned off **push_on_conversation**, is banned or not in a valid state, or ignores the sender. The API endpoints and the `fc:test-push` / `fc:generate-large-conversation` CLI tools no longer call `sendNotifications()` a second time. On 2.3 the extension now sends only the invite push ("X added you to the direct message …"), which no message insert covers, and sends it through the router like every other push. XenForo's own browser-push title for direct messages is no longer replaced with the board title.
- Direct-mode push jobs are keyed by content too, so two messages with identical text no longer collapse into one push.
- Verified on 2.2.19 and 2.3.7 by upgrading 1.8.7 → 1.8.8 and counting what reached a local stand-in for the hosted backend and for FCM. The recipient had one `direct` device and one `forumcopilot` device; pushes are counted as hosted / FCM. 2.3 with 1.8.7: create and reply from the app 3 / 1, from the web UI 2 / 1, invite 2 / 0, REST API 1 / 0; with direct mode only, the app still sent 2 hosted. 2.2 with 1.8.7: 1 / 1 everywhere except invite 0 / 0 and REST API 0 / 0. With 1.8.8, every create and reply (app, web UI, REST API, CLI) is 1 / 1 on both versions in hosted+direct mode, 1 / 0 hosted-only and 0 / 1 direct-only, and each recipient gets one e-mail. The `forumcopilot` device never got an FCM send. Invite is 1 / 1 on 2.3 and 0 / 0 on 2.2, as before.
- `markTopicRead` now marks threads read the way XenForo does, so members who read a thread in the app get the next watched-thread reply alert (and push) again. ### Added

### Changed
- **Thread view scroll performance.** Scrolling no longer rebuilds the whole thread: the visible-post counter and first-post flag are `ValueNotifier`s, rows are keyed by post id, and the per-post `VisibilityDetector` is gone. Post content is derived once per input and memoised in a process-wide LRU cache; the BBCode body is parsed to spans once per widget State rather than on every build. On the pinned benchmark thread, build p99 fell from 27 ms to 12–13 ms and in-place republishes (page load, reaction, poll vote) no longer produce a single build frame over 16.7 ms. ## [0.7.0] - 2026-05-08

Adds first-class support for **BYO Firebase + direct dispatch** push notifications. White-label and self-hosted forks can now run push without standing up a separate dispatcher backend — the ForumCopilot xenForo addon (v1.3.4+) ships its own FCM HTTP v1 client and dispatches directly using a service-account JSON.

### Added
- New `IFCDeviceProxy` SDK interface and `XenForoDeviceProxy` implementation, exposing `registerDevice` / `unregisterDevice` / `updateDeviceToken` against the `forumcopilot.php` plugin endpoint. Used by direct-mode builds to register an FCM token with the customer's own XenForo server (writes to `xf_fc_device_token`).
- New `AppForumConfig.pushSource` constant gating which push registration path runs at app startup. `'forumcopilot'` (default) keeps the existing hosted-backend flow. `'direct'` activates the new direct-mode flow described above.
- `PushNotificationController` now performs direct-mode device registration on init when `pushSource == 'direct'`, watches login state to retry once the user authenticates, and re-registers on FCM token rotation. Calls `unregisterDirect()` cleanly on logout.
- `SiteProxyService.getDeviceProxy()` shortcut for direct-mode callers.

### Changed
- `PushNotificationService.registerDeviceForSite`, `updateDeviceToken`, and `testConnection` now short-circuit to a no-op when `pushApiBaseUrl` is empty. BYO-direct builds set the URL empty since there is no hosted backend, and the previous behavior was to spam logs probing a non-existent URL.
- `README.md` push-notifications section rewritten as three labelled setup paths (hosted / BYO direct / BYO custom backend) with a comparison table, replacing the previous two-option layout that pushed self-hosters toward running a custom backend they didn't actually need.

### Notes for forks
- This release is **backward compatible** for builds already configured with `pushApiBaseUrl` and the hosted ForumCopilot Push backend — `pushSource` defaults to `'forumcopilot'`, behavior is unchanged.
- To opt into direct mode: set `pushSource = 'direct'`, set `pushApiBaseUrl = ''`, and configure the addon's "Direct push" admin options with a Firebase service-account JSON path. See README.md "Path 2" for the full walkthrough.
- The XenForo addon must be at least version 1.3.4 for the direct-dispatch endpoint to exist on the server.
